# Secure token storage — Witness Participate

**Owner:** Engineering (Mobile release programme)
**Status:** Active — implemented and unit-tested; not yet verified against a real device Keychain/Keystore

Where the participant capture token lives on a device between app launches,
what actually protects it, and what does not.

**Do not assume "a Capacitor storage plugin" implies Keychain/Keystore.**
Capacitor's own `@capacitor/preferences` plugin — the obvious first choice —
is explicitly **not** secure storage: on iOS it is backed by `UserDefaults`,
and on Android by plain `SharedPreferences`. Neither is encrypted at rest.
Using it for a capture token would have been storage-in-name-only. This app
does not use it for anything credential-shaped.

## What this app actually uses

`apps/participant-mobile/src/lib/secure-capture-session-store.ts`, backed by
[`@aparajita/capacitor-secure-storage`](https://github.com/aparajita/capacitor-secure-storage)
v8 (Capacitor 8-compatible). Verified from that plugin's own documentation —
not assumed:

| Platform | Mechanism |
|---|---|
| iOS | The encrypted system Keychain, scoped to this app's bundle ID. |
| Android | `SharedPreferences` values encrypted with AES-256-GCM, using a key generated by and held in the Android Keystore. |
| Web (`vite dev` only) | The plugin's own fallback: plain, **unencrypted** `localStorage`. This app never ships as a hosted website, so this path never runs in a shipped build — `createSecureCaptureSessionStore` prints a loud `console.warn` whenever it detects a non-native platform, specifically so this can't silently degrade unnoticed during development. |

This app implements **no cryptography of its own** — every encryption/key
operation happens inside the OS-provided Keychain/Keystore, per the governing
instruction's "Do not implement custom cryptography."

## What is stored, and what is not

Only `CaptureSession` (`@witness/participant-client`'s port):
`sessionId`, `workspaceId`, `participantId`, `captureToken` — see
`STORE_PRIVACY_DATA_MAP.md` for the full data inventory. Nothing else goes
through this store. In particular:

- The **join token** (from a deep link) is never persisted here — it exists
  only in memory for the duration of the `JoinScreen` flow, then is
  discarded once `joinSession` succeeds and a `CaptureSession` (containing
  the capture token) is saved instead. A join token cannot be replayed from
  storage because it is never in storage.
- The **current session id** (which key to `load()` on next launch) is
  stored separately, in ordinary `localStorage`
  (`apps/participant-mobile/src/lib/current-session-pointer.ts`) — a session
  id is not a credential (it grants nothing by itself; every actual API call
  still requires the capture token from secure storage), so it does not need
  Keychain/Keystore protection, and forcing it through the same store would
  have added unnecessary native round-trips for zero security benefit.

## Threat model

**Protects against:** another app on the same device reading the capture
token (both platforms' storage is app-scoped), and casual inspection of an
unencrypted preferences file (there isn't one — Android's underlying
`SharedPreferences` file is encrypted).

**Does not protect against:** a jailbroken/rooted device with an attacker who
already has that level of access, or a live, unlocked, physically-held
device with the app in the foreground — the same limits any OS-backed secure
storage has. This is a reasonable bound for a session-scoped participant
credential (not, e.g., a long-lived account password).

**The one real asymmetry, stated honestly:** the plugin's own docs note that
iOS does **not** delete Keychain data when the app itself is deleted — "since
only apps with matching app IDs can access this data, this presents no
security risk" per the plugin's own reasoning. Android, by contrast, deletes
all app data (including this store) on uninstall. In both cases the *value*
of a lingering entry is bounded independently: a capture token is
session-scoped and the backend already enforces expiry/revocation
(`participant-capture.live.test.ts`'s "THREAT: an expired capture token is
rejected" / "THREAT: a withdrawn participant cannot continue capturing"
tests) — a stale local Keychain entry for a session that has since closed,
or a participant who has been withdrawn, authenticates against nothing once
the server-side row is gone or the token has expired. Reinstalling the app
after deleting it on iOS would therefore restore a token that either still
works (session still open, participant still active) or is rejected
server-side exactly as if it had never been stored at all — never a way to
regain access the backend intends to have revoked.

## Token lifetime and deletion

- **Written:** once, immediately after a successful `joinSession` call
  (`App.tsx`'s `handleJoined`).
- **Read:** on every native app launch with no deep link present, to resume
  an in-progress session (`App.tsx`'s mount effect).
- **Deleted:** explicitly, via `secureStore.clear(sessionId)`, the moment the
  backend authoritatively reports the capture token as invalid (401/403 on
  `getParticipantCaptureContext` — `CaptureScreen`'s `onTokenInvalid`
  callback, wired through to `App.tsx`'s `handleTokenInvalid`). The app never
  infers invalidity from a network failure (`ApiError` with `status: 0`) —
  only from an authoritative rejection — so a temporary offline period never
  causes a false deletion of a still-valid credential.
- Otherwise persists indefinitely on the device, bounded by the server-side
  expiry/revocation behaviour described above, not by any client-side TTL —
  there is no product reason for the *client* to expire a session the
  facilitator hasn't closed and the participant hasn't been removed from.
